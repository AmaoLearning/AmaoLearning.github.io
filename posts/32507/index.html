来自高并发优化任务的Agentic开发经验

MaoCaiMao 发布于 2026-09-23

  • 📒 杂谈

Agent Fleet 高并发优化复盘：让 Agent 写代码之后，人需要掌握什么

当 Agent 承担越来越多的实现工作，人需要建立一套稳定的判断方法：看清问题，定义契约，理解取舍，并用证据决定下一步。

日期：2026 年 9 月 23 日。

这次我们为 Agent Fleet 的 YiCloud OpenSandbox 命令执行链路增加了异步方案，目标是降低高并发时管理长命令的资源开销。方案主要由 Codex 设计和实现，人负责决策。由此产生了一个值得长期关注的问题：如果实现能力已经可以委托给 Agent，人应该怎样理解、判断和推进一个后端项目？

本文整理这次讨论中值得复用的工程经验，以及后续学习资料。具体技术依据见 Issue #186、设计评论和实现提交。

1. Agentic Backend Development Experience

本任务属于后端基础设施开发，涉及分布式系统问题，完成该任务所需要的角色有：

  • 需求负责人：为什么要做？做到什么程度值得？
  • 系统设计者：什么部件负责什么？如何协作？
  • 后端开发者：怎样把设计落实为可靠代码？具体采取什么实现？
  • 测试工程师：怎样证明正常和异常情况都符合要求？
  • 性能工程师：资源到底花在哪里？优化是否有效？
  • 可靠性工程师：失败后怎么办？如何安全发布？

Agent协作中，人通常负责需求和技术决策，最有价值的参与方式是每项重要选择都回答：

它解决什么问题？付出什么代价？凭什么相信它有效？

而对于开发来说，需要把需求和解决方案分开思考。

1.1 需求侧

现在的距离目标主要远在哪里或者问题主要出现在哪里？

所以需要先复现问题、分部件测量目标或者问题。

一个合格的需求描述：

在相同命令、输出完整性和清理要求下，降低高并发时本地管理命令的资源开销，并量化短命令延迟的变化。

1.2 方案侧

新方案在互联网架构中属于“异步请求-回复”模式（Asynchronous Request-Reply pattern, guide from Microsoft）。

在契约层面，新方案将控制通道与数据通道通过不同的opensandbox API分工，让两者能够保持不同的设计特点。

新方案用状态机管理命令流程，它能明确记录：

当前处于什么阶段？现在收到这个消息，应该怎样处理？

其实现中的关键为：

  • 状态记录：程序记住了什么，例如执行ID、是否提交、是否终止；
  • 状态转换：什么证据允许进入下一阶段；
  • 异常出口：在哪些情况下必须停止正常流程。

新方案有一定的预算管理，这对于异步系统非常重要，因为程序可能同时提交过多任务。原方案中包含3类预算：

  • 时间预算：一次命令的总期限，包含排队、提交、等待和输出读取，便于整体等待不会超出预期；
  • 并发预算：名额控制同时管理多少条命令，HTTP连接池控制同时发出多少网络请求，轮询速度需要平衡响应速度与服务压力；
  • 清理预算：本地取消任务后仍需要向远端发送中断并确认结果，本地任务完成后也需要清理无用日志等。

严谨的测试环节需要多个步骤，每一层测试能回答的问题不同：

  • 单元测试：本地逻辑符合预期；
  • 真实接口测试：服务端行为符合假设；
  • 故障与生命周期测试：异常后仍然可控，如下载时取消、进程树中断等；
  • 性能对比：相同功能下资源和延迟怎样变化，如不同并发下的内存占用；
  • 完整流程测试：各组件组合后能否真正工作，如e2e测试是否达成目标。

1.3 理想流程总结：

  • 调查：要求当前调用链、资源测量和问题证据，决定是否值得优化；
  • 明确需求：发现必须保留的行为、成功指标和范围，决定哪些取舍可以接受；
  • 验证能力：实测上游API、明确已知限制，决定制定方案前的现实基础；
  • 设计：制定正常流程、失败流程和资源预算，决定复杂度与风险是否合理；
  • 实现：采取小范围改动、测试、撰写配置说明，需要决定能否进入真实验证；
  • 验收：要求正确性、故障、性能和完整流程证据，决定是否扩大试用；
  • 发布：确定启用范围、监控指标和回滚条件，决定是否能够成为默认方案。

委托Agent示例：

先调查当前执行链路与资源开销，列出必须保留的行为。基于真实接口能力提出方案，说明提交结果不明、超时、取消和输出完整性如何处理。实现后分别提供单元测试、真实接口、故障回收和公平性能对比的证据；区分已实现、已验证和未完成，再建议是否默认启用。

关键问题：

  • 问题的证据在哪里？
  • 调用方依赖的行为是否完整保留？
  • 网络中断后，系统怎么判断下一步？
  • 谁负责停止任务和收回资源？
  • 哪些证据足以支持扩大使用范围？

这都是消除不确定性的有效追问。

个人使用agent的经验:

与直连等待 / 异步轮询模式的区别类似，有长任务时，启用/goal类似直连、agent倾向于自主轮询，默认轮询时间短（几分钟一次），非常消耗token；而让agent把实验挂起后detach，必要时启动监控脚本，由人在需要时主动发起进度查询，这种方式可能不能及时发现错误，但是对于服务稳定的程序（有超时fallback、重试、日志记录等等机制），只需要查询日志即可。

2. 推荐阅读与开源实践

学习方向可以围绕两项能力展开：使用 Agent 开发可靠软件，以及为 Agent 构建可靠后端。以下资料按实际工程经验、代码可检查性和学习适配度选择，不代表统一的口碑排名。

2.1 Simon Willison博客guide：学习如何与编码 Agent 合作

Agentic Engineering Patterns

最适合先读。它涵盖 Agent 协作、Git、测试、反模式和代码理解。建议从 Writing code is cheap now、First run the tests、Linear walkthroughs 和 Interactive explanations 开始。

重点学习如何建立开发习惯、取得验证证据，以及让 Agent 帮助自己理解代码。

2.2 AWS Builders’ Library：建立后端可靠性常识

  • Timeouts, retries, and backoff with jitter
  • Making retries safe with idempotent APIs

这两篇解释超时、重试压力、退避和重复副作用。它们与本次长命令优化直接相关，也适用于普通 API、数据库周边服务和支付等远程操作。

适合带着“为什么有些操作能重试，有些不能直接重试”这个问题阅读。

2.3 Anthropic Engineering：组织长期 Agent 开发

  • Building effective agents
  • Effective harnesses for long-running agents

前者讨论 workflow 与 agent，以及何时增加复杂度；后者讨论跨会话接续、功能清单、进度记录、增量提交和端到端验证。

值得借鉴的是让进展可接续、完成可验证的方法。文章中的具体流程有其项目背景，应结合自己的仓库调整。

没什么具体实践，只有概念描述。

2.4 FastAPI 官方全栈模板：认识完整后端项目

fastapi/full-stack-fastapi-template

项目包含 API、数据库、身份认证、测试、容器和 CI/CD 配置，适合作为后端基础地图。

建议选择一个接口，沿着数据模型、数据库操作、测试和部署配置阅读。模板提供起点，业务权限与运行环境仍需单独设计。

2.5 Temporal：理解长流程如何恢复

  • Building an agentic system that’s actually production-ready
  • temporalio/samples-python

Temporal 关注持久化执行，帮助长流程在 worker 故障或重启后恢复推进。可以从官方示例的 hello、polling、message_passing 入手。

适合用来思考：调度进程重启后，任务状态和后续步骤如何恢复？博客带有产品立场，是否引入框架需要结合需求和运维成本；外部副作用的幂等性仍需设计。

2.6 Pydantic AI：把模型能力接入后端工程

pydantic/pydantic-ai

适合学习类型化工具与输出、依赖传递、测试评估和持久化执行集成。先读一个小示例及其测试，再扩大范围。

需要保留一个边界：类型校验可以约束数据结构，业务判断是否正确仍然需要验证。

2.7 如何把阅读变成自己的经验

建议按 Simon Willison → FastAPI 模板 → AWS → Anthropic 长期 Agent 文章 → Temporal → Pydantic AI 的顺序学习。

每读一篇，继续使用同一个项目做练习：

选出本文三个与我们的项目直接相关的原则。分别指出对应代码、解决的故障场景，以及现有测试能证明什么。区分当前实现、尚未验证的假设和可选改进，并给出一个反例帮助我理解。

持续用真实项目验证这些原则，可以逐步积累一套属于自己的工程判断：什么时候需要增加机制，什么时候证据还不够，以及什么时候可以放心地推进下一步。
